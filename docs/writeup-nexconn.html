Shade Guard

A buyer–store support chat on the Nexconn Chat SDK where an AI agent drafts the store's replies, and the chat itself stops a drafted reply from going out after the customer has moved on. The worked case: a shopper with an opened foundation in the wrong shade talks to the store's returns desk; the agent drafts the reply with the colour numbers in it; only staff send, approve or close, and only the shopper accepts.

Why we built it

The communication problem. An agent-drafted support reply is written against the thread as it stood when the agent read it. In a live chat the customer keeps typing, so a draft that staff approve a minute later can answer a question she has already changed. Most support copilots stop at "approve and send". Shade Guard adds three checks on Nexconn itself: every staff send, note, approval and close first reads the thread back from Nexconn's history and is refused (thread_moved) if she has written since the draft; a message that lands while a send is on its way is flagged on the desk afterwards ("Sent over a message you had not seen"); and an exchange can't be approved until she taps Accept on the offer card in the chat (not_accepted). The beauty return below is the worked example.

Foundation is bought by colour, and colour is the one thing a product photo can't show on your skin. When an online shopper guesses wrong, the store hears about it in its support chat: "this is the wrong shade, and I've opened it." Opened cosmetics generally can't be resold for hygiene reasons, so refunding one means writing the unit off. An exchange to the right shade keeps the sale, but only if someone can say which shade is right, with numbers the shopper can check.

That conversation is where an AI agent is both tempting and risky. It can read the order and do the colour arithmetic in a second. It can also promise a refund nobody approved, answer a question the shopper has already moved past, or push an exchange she never agreed to. Shade Guard puts the agent's speed into the draft and keeps every message that commits the store in a person's hands, and the chat itself enforces that: it is not a guideline staff are asked to follow.

The agent here is a deterministic planner, not a language model, and the guard does not depend on that. It is structural: the agent's draft_reply tool has no text field, the agent's tools get no chat transport at all, and a test (tests/chat-boundary.test.js) keeps every module they import away from it. A language model behind the same tools would meet the same refusals.

What it does, in the order a judge sees it

  1. The live demo opens the returns desk on the left and the shopper's phone on the right. They are two separate apps, two frames of one page, each connected to Nexconn as its own fictional demo user; they share nothing but a Nexconn direct channel.
  2. As Maya (order O-5521, Skin Tint 220N), tap Start a return: wrong shade, opened. The request reaches the desk over Nexconn, showing its server time and its message id.
  3. The agent reads the thread and the shade reading stored on her order, and drafts an exchange offer for 245W that lists the order's three closest shades: 245W at ΔE00 2.10, 250W at 3.51 and her 220N at 5.00. The draft sits on the desk, marked Not sent.
  4. As Maya, ask "is 250W any closer?" before staff send. Staff click Send: the desk reads the thread back from Nexconn first, finds her message, and refuses (thread_moved). Her question is now on screen, and the agent drafts again.
  5. Staff answer in their own words from the numbers on screen (Send note), then send the offer. On the phone it arrives as an offer card with an Accept button.
  6. Approve exchange before she accepts is refused (not_accepted). She taps Accept; staff approve the exchange and close the case.
  7. Switch the phone to Asha (order O-5530, no reading). Her return arrives in the desk's second channel, and the desk marks her case unread. The agent can only draft an invitation to check her shade; staff send it. Her own tap runs the check (on the app's sample face) and Share my reading sends the result as a numbers-only card. The agent then drafts the exchange that reading supports.
  8. Reload either side: the thread comes back from Nexconn's message history, the closed case included.
  9. Try it as the agent, under the desk's thread, sends the agent's own calls to send, note, close and accept, and a draft with free text: each is refused at the chokepoint, and the message count read from Nexconn is the same before and after.

The rule the chat enforces: the agent drafts, people decide

The agentPeople
Read the support threadread_thread, as recorded from Nexconn—
Draft a replydraft_reply: the text is composed in code from the reading's own numbers; it takes no free text—
Send anything to the shopperNever. A draft never reaches NexconnStaff: Send (the draft) or Send note (their own words)
Share a shade readingNeverThe shopper: Share my reading, numbers only, never a photo
Accept an offerNeverThe shopper: Accept on the offer card
Approve an exchange or refund, close a caseNeverStaff, and an approval only after her Accept

People's verbs are never registered as tools the agent can find, and the chokepoint refuses them for the agent if it calls them directly. An agent tool is handed no chat connection at all, and a lint rule keeps the agent's code from importing one. What is checked at the moment of each click, on Nexconn's own message ids and server times, never the local clock:

thread_moved
The thread read from Nexconn holds a shopper message the draft, or the screen, had not seen. Nothing is sent; her message is shown; the agent can draft again.
not_accepted
An approval with no acceptance from her for the newest offer, an empty thread included.
offer_superseded
She can accept only the newest offer in the thread.
already_sent
A second click on Send, or a retry whose first answer was lost: the offer already on Nexconn is not sent twice.
thread_unverified
The desk could not read the thread from Nexconn, so it sends nothing.
chat_offline
The connection dropped; nothing is sent while offline.
wrong_actor
The agent calling a person's verb, or a shopper calling a staff verb.
smuggled_field
Free text slipped into the agent's draft call.

One round trip remains between the read and the send, and no chat service closes it. So after every staff send, the desk compares positions in the thread by server time and message id, and a shopper message that landed in between flags the case "sent over a message you had not seen".

How it is built

  • One chokepoint. Every button and every agent call goes through invoke(tool, args, actor): the same mutation, then a redraw. The chat connection is handed only to people's verbs.
  • The SDK in the page, not in the repository. @nexconn/chat and @nexconn/engine 26.2.1 load at run time from jsDelivr through an import map, each pinned by an integrity hash, under Nexconn's own licence. The repository stays MIT and copies no SDK file.
  • Tokens. A script on Node built-ins signs Server API calls with the App Secret, which stays in a file outside the repository, to register the demo users and issue their tokens.
  • Nothing installed. Node built-ins on the server and plain ES modules in the browser; the only third-party code is the Nexconn SDK, which loads from jsDelivr at run time under Nexconn's licence. 419 offline tests run against a fake chat service that has its own message ids and server times, delayed delivery and paged history, so every refusal above has a test.
  • A deterministic planner, not a language model. Every figure in a draft is the reading's own number, which the evidence must match within 0.05 or the draft is refused.
  • The colour science is the original build's code: sRGB to CIELAB to CIEDE2000, tested on all 34 published CIEDE2000 reference pairs.

Traction, stated plainly

What the App Key's usage can confirm. On 22 Nov 2026 the demo's own user ids connected to this app live from Bengaluru, and real messages crossed Nexconn: 45 timed notes on one seat, both cases end to end for the film (from the public Pages demo), and the first-run checks, each with Nexconn's own message id and server time on screen (see "Measured on the live app"). The console's usage page, read the same day, still showed 0 monthly active users: it was last refreshed on 21 Nov, 15:59 UTC, before the app existed. Whatever it shows later is not people. Nexconn counts the unique user ids that connect, and the public demo shares 12 fictional seat ids (four seats, each a desk and two shoppers) among everyone who opens it, plus 2 ids registered for tests. However many judges open the demo, the count stays at those ids. No users were recruited and none are claimed.

Can it become a product?

  • Who uses it. The support desk of an online beauty or personal-care store that handles wrong-shade returns in its support chat, and the shoppers on the other side.
  • What changes for them. A question like "is 250W any closer?" gets a number from the shopper's own reading instead of a guess. An opened unit can be offered as an exchange, with the evidence on the order, instead of being refunded by default. The agent does the arithmetic and the drafting and cannot commit the store: no send, approval or close happens without a person, and no send goes out over a message staff have not seen.
  • What a store plugs in. Its own chat on Nexconn (the SDKs cover web, iOS, Android and Flutter); its order system, where the reading is stored as numbers; measured swatch colours for its own ranges; and a live colour provider for the shade check. Shade Guard's YouCam provider is written and has not yet called YouCam.
  • Who would pay, and what adopting it takes. The intended buyer is the store, as an add-on to the support chat it already runs, paid per support seat or per resolved return. Adopting it replaces the public demo seats with signed-in shoppers, each with a Nexconn token issued by the store's own server, and wires the approval to the store's returns system instead of a simulation.
  • A first pilot. The desk drops into a store's existing Nexconn support chat as six custom message types and two agent tools. A pilot store would count two things on its wrong-shade returns: how many end as an exchange instead of a refund, and how many stale sends the thread_moved check refused. The first production change is a Nexconn user issued per shopper by the store's own server, in place of the 12 shared demo seats, so real use shows up as real active users. No market figure is claimed here.
  • What the merchandiser already gets. Every "no close match" reading is kept as numbers and listed as a range gap in the merchant panel, so the store learns which shade its range lacks.

What this entry does not claim

  • No users. The active-user count is the demo's own fictional seat ids and test ids.
  • No real face reading. The shade check runs on the app's synthetic sample face and says so on screen.
  • No real store, money or stock. The store, the orders, the shoppers and the approvals are fictional; an approval is simulated, and after a reload an approved case shows as open again.
  • No language model. The agent is a deterministic planner; every number in a draft is the reading's own, composed in code.
  • No authenticated shopper. The demo's seat tokens are public, so "her own Accept" means a message from the seat's shopper user in that visit. The visit id keeps two honest visitors on one seat apart; it does not stop a hostile one.
  • The live chat has an end date. The demo tokens stay valid until Wed 2 Dec 2026, after judging, when they are expired; from then the chat panes read Offline.

Try it in 90 seconds

  1. Open guptachetan1995.github.io/shade-guard/chat.html. Wait for both badges to read Connected. If the page says the seat is busy, click Open another seat.
  2. On the phone, tap Start a return: wrong shade, opened. Watch the request and the agent's draft appear on the desk.
  3. On the phone, write "is 250W any closer?" and send it. On the desk, click Send: it is refused, and the agent drafts again.
  4. On the desk, write a note in your own words and click Send note; then Send the offer and click Approve exchange: refused until she accepts.
  5. On the phone, tap Accept. On the desk, Approve exchange, then Close case.
  6. Optional: Switch to Asha's phone for the case with no reading; reload either side; open Try it as the agent on the desk.

The code runs from a fresh clone with nothing to install: npm test runs every test offline, and npm start -- --fake-chat walks the same path on an offline stand-in that says on every pane that it is not Nexconn.
